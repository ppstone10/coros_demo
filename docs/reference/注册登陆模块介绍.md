# 项目全景介绍

本项目是基于 **Kotlin Multiplatform + 三端原生 UI** 的跨平台移动应用，包名 `com.example.demo`。核心业务逻辑（模型、校验规则、状态管理、本地 mock 数据源）全部放在 `common/` 中，与平台无关。Android 用 Jetpack Compose、iOS 用 SwiftUI、鸿蒙用 ArkUI 各自实现原生界面。

项目采用 **SDD（Spec-Driven Development）** 流程——功能变更必须先写 Spec 定义行为，再写测试，最后实现。**三端同步原则**：影响 UI 结构、行为或架构的变更必须在 Android/iOS/HarmonyOS 三端同步实施。

所有数据均为本地 mock，数据契约由 Protobuf 定义，JSON 持久化受 Proto 字段约束。不接入真实后端，避免泄露敏感信息。

## 项目的四个核心架构决策

1. **KMP 共享业务层**：平台无关的模型、规则、UseCase、Repository 抽象、本地 mock、状态容器和共享测试
2. **三端原生 UI 框架**：Android Compose、iOS SwiftUI、鸿蒙 ArkUI，各端保留原生体验和平台能力自由
3. **SDD 流程驱动**：所有变更先写 Spec、更新 TRACE、写测试、再实现，AI 也遵循同一约束
4. **鸿蒙独立桥接**：通过独立 KNOI bridge 项目编译 commonMain 源码为 libkn.so 供 ArkTS 调用，不维护 ArkTS 业务 fallback

## 1. 技术路线：KMP + 原生 UI

这是项目最重要的技术路线。

| 平台 | UI 技术 | 共享业务接入方式 |
| --- | --- | --- |
| Android | Kotlin + Jetpack Compose | 直接调用 KMP common |
| iOS | Swift + SwiftUI | Shared.framework + Swift Adapter |
| HarmonyOS | ArkTS + ArkUI | KNOI Bridge + libkn.so |

Android 的 Compose、iOS 的 SwiftUI、HarmonyOS 的 ArkUI 都有成熟生态，保留原生 UI 更利于体验与后期维护。

账号格式校验、密码规则、验证码有效期、注册登录、会话失效、错误码等业务规则在 `common` 中维护。Android 和 iOS 直接使用 KMP 产物；HarmonyOS 由独立 bridge 编译同一份 `commonMain` 纯业务源码。

## 2. 核心架构：MVVM + 单向数据流

项目采用分层组合架构。三端 UI 层采用原生 MVVM：页面负责展示，平台 ViewModel 负责连接 UI、导航和共享业务。共享业务层采用 MVI 风格的单向数据流。

**注册登录模块**的用户操作统一抽象为 LoginAction，由 LoginStore 处理，并输出 LoginState 和 LoginEffect。Android 的 AuthNavGraph、iOS 的 AuthRouter、HarmonyOS 的 AuthNavigator 分别消费一次性业务事件，使用各自平台的原生导航完成页面跳转。

**健康看板模块**采用同样的 MVI 模式。HealthDashboardStore 接收 HealthDashboardAction（切换场景、编辑卡片、刷新数据），输出 HealthDashboardUiState 和一次性 Effect。Android 的 HealthDashboardViewModel、iOS 的 HealthDashboardViewModel、HarmonyOS 的 health ViewModel 分别消费状态，三端 UI 各自渲染重组。

两个模块的共性：common 中只有 Store、UseCase、Rule 等纯业务逻辑，不操作页面导航；各端 ViewModel 负责桥接，导航由平台原生能力处理。三端页面实现不同，但业务规则只维护在 common 中，实现业务一致、UI 原生、架构可扩展。

可以展示这个结构：

逐个说明职责：

- **common**：核心业务层，只放与平台无关的逻辑。
- **androidApp**：Compose 页面、导航、Android 本地存储。
- **iosApp**：SwiftUI 页面、Swift ViewModel、KMP Framework 适配。
- **harmonyApp**：ArkTS/ArkUI 页面和导航。
- **harmony-kmp-bridge**：将 KMP 的 Kotlin 逻辑编译为 HarmonyOS 可调用的 libkn.so。
- **docs**：记录架构边界、平台接入方式和开发流程。

可以强调共享层边界：

> common 不依赖 Android SDK、iOS API、ArkUI 或 Compose。它只关心业务模型和业务规则，因此可以被不同平台复用。

## 4. 各端接入共享业务层

### 注册登录模块

common 主要包含：

- **LoginRules**：账号、验证码、密码等输入规则
- **LoginModels**：账号、会话、资料、错误码、Action、State、Effect
- **LoginStore**：状态机和 Action 分发
- **LoginUseCase**：登录、注册等业务编排
- **AuthRepository**：认证数据接口
- **LocalMockAuthRepository**：本地 Mock 实现
- **LoginFacade**：跨语言调用门面
- JSON 序列化与反序列化逻辑

#### Android

Android 本身使用 Kotlin，所以可以直接调用共享模块中的 LoginStore、LoginRules、LoginAction 和 LoginEffect。

Compose 页面通过 LoginViewModel 管理 UI 状态，导航由 Compose Navigation 处理。

#### iOS

iOS 通过 KMP 导出的 Shared.framework 调用共享业务。为了不让 SwiftUI 页面直接依赖 Kotlin 的复杂类型，我们使用 LoginFacade 提供简单稳定的业务方法，例如请求验证码、校验验证码、提交登录、登出、读取状态。SharedLoginAdapter 再将 Facade 包装成 Swift 风格接口，Swift ViewModel 最终只依赖 Adapter。

#### HarmonyOS

HarmonyOS 的 UI 仍然完全使用 ArkUI 原生实现，但不会再复制一份 ArkTS 登录业务逻辑。harmony-kmp-bridge 将 Kotlin 业务编译成 libkn.so，并通过 KNOI 生成 ArkTS 调用接口。ArkTS 的 KnoiLoginAdapter 只负责调用 Bridge、映射状态、处理持久化和页面提示。真正的账号校验、验证码、注册、登录、会话逻辑仍然执行在 KMP common 中。

HarmonyOS 保留 ArkUI 原生页面，但不复制登录、注册、验证码和会话规则；页面层只负责展示、导航与平台能力适配，业务规则仍只有一份。

### 健康看板模块

common 主要包含：

- **HealthDashboardStore**：看板状态管理和 Action 分发
- **HealthDashboardUseCase**：多源 mock 数据收敛为 DashboardUiState
- **HealthDashboardModels**：DashboardUiState、HealthCardUiModel 等
- **HealthRules**：健康数据校验规则
- **HealthFacade**：跨语言调用门面
- **LocalHealthDashboardDataSource / JsonHealthDashboardStateDataSource**：本地持久化
- **HealthMockContracts**：Proto 与 Domain 双向映射

#### Android

HealthDashboardViewModel 直接调用 HealthDashboardStore 和 HealthDashboardUseCase。Compose 页面通过 StateFlow 订阅 DashboardUiState，导航由 Compose Navigation 处理。

#### iOS

SharedLoginAdapter 同构的 SharedHealthAdapter 包装 HealthFacade，SwiftUI 的 HealthDashboardViewModel 消费 adapter 输出的状态，渲染 HealthDashboardView。

#### HarmonyOS

与登录模块同理，通过 HarmonyHealthService（KNOI bridge 生成）暴露 store 方法，ArkTS 的 KnoiHealthAdapter 调用 bridge 并映射状态到 ArkUI 页面。

## 5. 数据持久化与可恢复性

项目有两个独立的持久化领域，各自由 Proto 定义字段契约，common 层提供统一编解码，平台层只读写字符串。

### 认证数据持久化

账号库、当前 Session、验证码状态和用户资料保存为 JSON。`auth_mock.proto` 是字段契约，`MockAuthStoreJson` 是统一编解码入口。

| 平台 | 存储实现 |
| --- | --- |
| Android | SharedPreferences + JSON |
| iOS | UserDefaults + JSON |
| HarmonyOS | ArkTS StorePersister + JSON Snapshot |
| 测试 | 内存数据源 |

### 健康看板数据持久化

看板配置（启用的卡片类型及顺序、场景选择）以 `health_dashboard_mock.proto` 为字段契约，按认证 userId 分区保存。

| 平台 | 存储实现 |
| --- | --- |
| Android | 独立 SharedPreferences（与认证分开） |
| iOS | UserDefaults + JSON |
| HarmonyOS | ArkTS Preferences |
| 测试 | 内存数据源 |

登出仅阻断访问，账号注销时可清除该用户分区。

### 架构价值

> 业务层只依赖 DataSource 抽象，不关心数据最终写到 SharedPreferences、UserDefaults 还是 HarmonyOS Preferences。两个模块当前都只使用本地 mock；如未来接入真实服务，应在独立项目或分支重新设计。

## 6. 测试与质量保障

### 注册登录模块

#### 第一层：规则测试

对应 `LoginRulesTest`，当前共 7 条共享规则测试。

测试内容：

- 手机号格式、规范化处理
- 邮箱格式校验
- 验证码必须为 4 位数字
- 密码长度和字母数字组合规则
- 两次密码一致
- Loading 状态下禁止重复提交

讲法：

这一层验证最基础的输入规则。例如同一个手机号、密码、验证码输入，在 Android、iOS、HarmonyOS 上都会调用同一套 LoginRules，因此不会出现某端允许、另一端不允许的情况。

#### 第二层：业务流程测试

对应 `LoginUseCaseTest`，当前共 28 条共享认证流程测试。

测试内容：

- 注册成功并创建 Session
- 重复注册
- 验证码错误
- 验证码过期
- 重发验证码替换旧验证码
- 正确与错误密码登录
- 修改密码
- 重置密码
- 完善资料
- 登出
- 会话失效
- 删除账号
- 应用重启后恢复 Session

讲法：

第二层验证完整业务流程。重点不只是"成功情况"，还验证了重复注册、错误密码、验证码过期、会话失效等真实异常场景。

例如验证码测试会先生成一个验证码，再推进模拟时间，验证共享层最终返回"验证码已过期"。这保证了验证码过期判断不是某个页面的倒计时，而是业务层的真实规则。

#### 第三层：数据异常与持久化测试

测试内容：

- 空数据
- 损坏的本地 Session
- JSON 序列化/反序列化
- 兼容旧字段命名
- 持久化保存失败

讲法：

第三层验证应用在本地数据不完整、数据损坏或保存失败时，能安全返回明确错误，而不是直接崩溃或保留错误登录态。

此外，`BusinessMockDataSourceTest` 验证后续业务必须通过 `AuthRepository.verifyBusinessAccess()` 获取当前 Session；未登录、登出和会话失效后均返回 `AuthRequired`。Android 另有 Instrumentation Test 验证 `SharedPreferences` 中的登录态可由新的数据源实例恢复。

### 健康看板模块

健康看板共享业务测试集中在 `common/src/commonTest` 中，覆盖三层。

#### 第一层：规则与数据验证

对应 `HealthRulesTest` 和 `HealthModelsTest`：

## 8. SDD 开发工作流

本项目严格遵循 **Spec-Driven Development**，所有功能变更闭环如下：

1. **读取既有知识**：先读 LEARNINGS.md、spec/TRACE.md，再读本次任务对应的 Spec
2. **先写或更新 Spec**：在 spec/ 中定义目标、非目标、边界、数据、行为、异常、测试和稳定规范 ID
3. **在 TRACE 中预留映射**：写测试或实现前，在 spec/TRACE.md 添加 ⏳ 行
4. **先写测试并确认红灯**：至少运行一次确认测试能捕获缺失行为
5. **编写最小实现让测试通过**：发现 Spec 缺口则先修订 Spec，再继续
6. **更新 TRACE、Worklog 和 Learnings**：填入稳定符号/测试名和验证命令

### 门禁脚本

```bash
./tools/check-sdd.sh         # SDD 文档完备性检查
./tools/check-docs.sh        # 文档治理规则检查
```

### common 测试

```bash
./gradlew :common:check
```

